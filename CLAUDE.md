# job-search-pipeline

Automated end-to-end job search orchestrator. Scrapes LinkedIn/Indeed via **JobSpy** (the only two supported boards — see the scrape-sites note under Configuration), scores results against a resume using YAKE keyword extraction, optionally screens for liveness, then bridges surviving jobs into **career-ops** for AI-powered evaluation. Supports interactive evaluation via any agent CLI (`--batch`) or synchronous parallel API evaluation across any LLM provider (`--evaluate-batch`).

**Applying is not a pipeline stage.** The pipeline finds and evaluates roles; the terminal `--handoff` stage — or the UI's **🤝 Hand off** button (batch) and per-role **Hand off** prompt in the report pane — emits an agent-agnostic **work-order per job site** (`next-roles-<site>.jsonl` + `.md` — one session per site the scraper searches from, written to `HANDOFF_OUT_DIR`, default `output/handoff/`) that the user hands to whatever browser agent they prefer (an agent CLI from [pipeline/agent_cli.py](pipeline/agent_cli.py), a desktop agent session, a local Agent-SDK runner, …). The agent works one site session at a time — logging into that site once, applying through the user's own logged-in browser — writes each outcome back into the session file's `status` column (`claimed` / `ready-to-submit` / `applied` / `handoff` / `skip:<reason>`; `handoff` means blocked on something only the person can do — a login, a CAPTCHA, a verification code), and the next `--handoff` run folds those into the **shared** status tracker (`role-status.jsonl`, board-insensitive keys) so a handled role never reappears on any site.

**What the agent does at the Submit button is the person's decision, not the agent's.** `HANDOFF_SUBMIT_POLICY` (`SUBMIT_POLICIES`, [pipeline/handoff.py](pipeline/handoff.py)) is one of three, and the default is the safe one: `stop-before-submit` fills and reviews every application, stops, and records `ready-to-submit`, so nothing is sent without the person seeing it; `submit-easy-apply` submits only the rows tagged `easy_apply` (Indeed Apply, LinkedIn Easy Apply — the flag `parse_applications` already computes from `data/easy-apply-urls.txt`) and stops before Submit on everything else; `submit-all` is the old behaviour. `review` / `easy-apply` / `all` are accepted as aliases on read and never rendered (`canonical_policy`). Every agent-facing surface states the active policy in one line (`policy_line`) — the handoff README, the work-order header, the kickoff prompt and the per-role prompt — because an agent that reads any one of them must know whether to click; and each renderer takes `policy=` as an explicit kwarg, resolving the env only when it is None, so a test passes a value rather than setting one. An unknown value in `.env` falls back to the default with ONE warning per distinct value per process, which is why `HANDOFF-README.md` and `RESUME-RUNBOOK.md` are now **rewritten on every bootstrap** rather than seeded when missing: they are ours and they state the policy, so seeding-only meant a policy change never reached a folder that already existed (`PROFILE.md` is the user's and stays non-clobber).

`ready-to-submit` is the one exception to "a handled role never reappears". It comes back at the **top** of its site's session on every run — before the fresh roles, in score order among themselves, with its jsonl `status` pre-filled and `resume_from` set — until the person records `applied`, and an untouched row folds back unchanged, so the file is the same the next morning. That idempotence is what `drop_late_writeback` now turns on: `run()` reads the work-orders twice (as writeback before the build, as `late` after tailoring), so a pre-fill is present in BOTH reads, and dropping on key membership alone deleted every re-emitted row at write time and made the work-order oscillate run to run. The rule is on the (`resume_from`, late status) pair — an unchanged pre-fill is kept with its rank, a key that has moved to any other status is dropped, a fresh row seen late at all is dropped as before (`tests/test_handoff.py::TestLateWritebackReady`). A ready role whose queue row is gone (moved on by hand, Discarded by the re-check) is not synthesized back: the queue is what is still actionable. And `ready-to-submit` stays **dedup-only** in the tracker, like `handoff` / `claimed` / `drafted` — career-ops has no canonical state for "awaiting the person's click", and inventing one would move the row past **Evaluated** before anything was sent; the row stays Evaluated (which is what keeps it in the queue to be re-emitted) and **Applied** is written when `applied` is recorded.

Terminal outcomes are reflected into career-ops' `applications.md` — the tracker the UI renders and the cloud maintains — (`applied`→**Applied**, `skip`→**SKIP**; `handoff`/`claimed`/`drafted`/`ready-to-submit` stay dedup-only, and a row already past **Evaluated** is never clobbered), which surfaces them in the UI Kanban and queues an **identity-anchored** pending override; the UI's **Push** then dispatches it to `edit-tracker.yml` so the cloud tracker matches. Handoff is a local-only stage (the daily cloud workflow never runs it), so applied status originates locally and flows *up* to the cloud, same as a manual Kanban edit.

## Pipeline stages

| Stage        | Script                      | Input → Output                                                            |
| ------------ | --------------------------- | ------------------------------------------------------------------------- |
| Scrape       | `pipeline/scrape.py`        | `config/search.yml` → `output/jobs.csv` (truncated when a run returns zero rows) |
| Filter       | `pipeline/filter.py`        | `output/jobs.csv` → `output/filtered_jobs.csv`                            |
| Screen       | `pipeline/screen.py`        | `filtered_jobs.csv` → filtered in-place + backfills missing descriptions  |
| Bridge       | `pipeline/bridge.py`        | `filtered_jobs.csv` → `career-ops/data/pipeline.md` + `scan-history.tsv`  |
| Batch prep   | `pipeline/batch_prep.py`    | bridge output → `career-ops/batch/batch-input.tsv` + `batch/jds/*.txt`    |
| Batch evaluate | `pipeline/batch_evaluate.py` | `batch-input.tsv` → parallel LLM evaluation → `reports/*.md` + `tracker-additions/*.tsv` |
| Handoff      | `pipeline/handoff.py`       | queue (scored-export jsonl if present, else `career-ops/data/applications.md`) + `role-status.jsonl` (+ optional prose JOB_LOG) → `output/handoff/next-roles-<site>.{jsonl,md}` (one session per site) for the user's browser agent |

`orchestrate.py` chains all stages. Each stage can be skipped independently via `--skip-<stage>`; `--handoff` opts into the terminal work-order build (`--handoff-board`, `--handoff-limit`, `--handoff-tailor`).

## How to run

```powershell
# Windows
./run.ps1                        # scrape → filter → screen → bridge → batch-prep
./run.ps1 --batch                # + evaluate interactively via your configured CLI
                                 # (BATCH_CLI in .env; pipeline/agent_cli.py owns the default)
./run.ps1 --evaluate-batch       # + evaluate via any LLM API (auto-detects provider from env keys)

# Select specific search passes — three mutually-exclusive flags:
./run.ps1 --evaluate-batch --only-pass "easy apply"   # explicit name match (errors on typo)
./run.ps1 --evaluate-batch --easy-apply-only          # passes with easy_apply: true (no-ops if none)
./run.ps1 --evaluate-batch --no-easy-apply            # passes without easy_apply: true

# Skip stages when re-running
./run.ps1 --skip-scrape --skip-filter --batch
./run.ps1 --skip-scrape --skip-filter --evaluate-batch

# Build the browser-agent work-orders — one session per job site
# (next-roles-<site>.jsonl). Queue = the scored-export jsonl when one exists,
# else career-ops/data/applications.md (so --recheck-liveness Discards keep dead
# roles out on the tracker path; the agent re-verifies postings live either
# way). --handoff-limit caps each site; --handoff-board narrows to one site;
# --handoff-tailor pre-tailors a resume per row.
./run.ps1 --skip-scrape --skip-filter --handoff
./run.ps1 --skip-scrape --skip-filter --handoff --handoff-board linkedin --handoff-limit 25 --handoff-tailor
```

```bash
# macOS/Linux
./run.sh --batch
./run.sh --evaluate-batch
```

A second guard pins every derived key to a real `onboard.html` field. That banner is a claim, so it degrades to naming the unreadable files when nothing could be read back. `search_entries` is the one app-side mirror of `scrape.load_searches`'s shape rule (`searches:` list vs legacy `search:`); `server._search_entries` adds only the save endpoint's validity rule on top, since two mirrors could drift into the save endpoint refusing a config the wizard prefills from. Two rules exist because prefill now reaches configs the wizard didn't write: **an unconfigured copy prefills nothing** (setup copies `search.example.yml` to `config/search.yml` before the user answers anything, so deriving from it unconditionally offered a first-time user the demo's Toronto passes and `senior, manager` roles-to-avoid as their own answers — with no edit-mode banner, since nothing is configured — and a Save wrote a search they never asked for); and **`search_detail_at_risk` names what a Save would drop**, since Save rewrites `searches:` wholesale from six form fields. That flattening cost nothing while only wizard-written configs got this far — rewriting one reproduces it — but a hand-written pass can carry `job_type`, `linkedin_company_ids`, a `country_indeed` the wizard re-infers differently, or a location the Locations field can't hold (`parse_locations` rejoins only "City, ST" pairs, so `Berlin, Germany` returns as two passes). It is deliberately precise, not exhaustive — it stays silent on every wizard-written config and on the shipped example, because a warning that always fires is wallpaper. `search_terms` is knowingly excluded: predicting whether the rewrite reproduces the current list means mirroring `expandSearchTerms` from `setup-profile.mjs` in Python. |
| `pipeline/rowio.py`                     | The one contract for "the previous **CSV** stage produced no rows": `read_rows(path)` (missing, zero-byte **and header-only** all read as `[]`) and `write_rows(path, rows, fieldnames=None)` (zero rows truncates the file to zero bytes). The rule is deliberately asymmetric — **producers write exactly zero bytes; readers accept anything with no data rows** — which is what lets it work against files it didn't write (a header-only CSV left by an older run, and scrape's happy path, where pandas owns the columns and writes via `to_csv`). Two neighbours are deliberately out of scope and say so in the module docstring: the `.tsv` queue/state files, whose `st_size == 0` answers "should I write a header" on a file that accumulates across runs, not "did upstream produce nothing"; and handoff's jsonl+md work-orders, where the markdown half renders an empty table on purpose because its reader is a human. Truncating is the load-bearing half — a stage that produced nothing today must not leave yesterday's output for the next stage to re-process as today's, and `--skip-scrape`/`--skip-filter` reuse whatever is on disk. Every "nothing survived" exit in scrape, filter and screen writes through it, and filter, screen and bridge read through it, so a producer and a consumer can't disagree about which shape means empty. Writes go via a temp file and `os.replace`, so a raise mid-write can't leave a header-plus-partial-rows third shape that reads as a complete short result. Reads decode `utf-8-sig`, so an Excel round-trip's BOM doesn't rename the first column out from under every stage. A dependency-free leaf (stdlib only) on the same terms as `sites.py`. |
| `pipeline/stdio.py`                     | The stage-log buffering rule, in one place: **every entry point calls `line_buffer_stdout()` first** — `orchestrate.main()` and each `__main__` block under `pipeline/` — and no `print` anywhere needs `flush=True`. Redirected to a file or pipe, Python block-buffers stdout at 8KB, so progress lines sit unseen and a run looks hung on exactly the slow steps someone is watching. The two config-merge shapes disagree about where the argv lives (OpenCode keeps it all in `command`; Antigravity splits `command` + `args`), and appending to the wrong one merges cleanly and launches nothing, so `_pin_entry` picks by type and `tests/test_agent_cli.py::TestChromiumIsPinned` drives all four CLIs. | `pipeline/remote_signal.py`             | The **remote-consistency guard**: a stdlib leaf (plus `sites.py` and `rowio.py`) holding one question — *does a posting the board flagged remote SAY so?* — and the one reading of the two flags it turns on. A board's remote flag is the employer's checkbox, not the JD, so an `is_remote: true` pass returns roles that are plainly on-site in another state, and those rows bypass every location check (`filter.is_eligible` returns True for a remote row) and burn an evaluation each. `REMOTE_SIGNAL_RE`/`mentions_remote` is deliberately plain — remote, remotely, remote-first, work from home, WFH, telecommute, telework, home-based, home office, fully distributed, distributed team, anywhere in the US/country — and `virtual` is deliberately OUT, because on-site JDs say "virtual interview" and "virtual care"; a hybrid JD mentions remote work and passes, which is intended, since the target is the posting that never says the word at all. `is_remote_str`/`remote_only_str`/`flagged_remote` read the `"True"`/`"False"`/`""` CSV cells the same way in filter, screen and bridge — the shape `bridge.is_easy_apply_row` already set for the third pass-level flag — and `guard_enabled(cfg)` reads the switch tolerantly, because a quoted `"false"` is a truthy Python string and the same expression written inline in two stages would eventually disagree. `local_pass_locations(cfg)` (the `searches:`/legacy `search:` shape rule `onboard.search_entries` uses, pinned to agree with it) and `location_eligible` — filter's location half, kept here so screen can re-apply it without importing filter, which pulls yake and pandas — are what keep a genuinely local on-site role that the remote pass happened to return. ## Configuration (`config/search.yml`)

```yaml
searches:
  - name: "pass name"
    search_terms: ["term1", "term2"]
    sites: [indeed, linkedin] # the only supported boards (see note below)
    results_wanted: 50
    location: "Dallas, TX"
    hours_old: 168 # mutually exclusive with job_type/is_remote/easy_apply on Indeed
    # is_remote: true   # a second group — uncommenting either of these makes the
    # easy_apply: true  # pass conflict with hours_old on Indeed, which is then
    #                   # dropped from the pass; LinkedIn still runs it as written
    linkedin_fetch_description: false # see "Description backfill" below

filter:
  target_titles: ["Senior Software Engineer", "Staff Engineer"] # +5 score bonus
  negative_titles: ["intern", "director", "VP"] # hard-exclude
  min_score: 5
  max_age_hours: 168
  keyword_overrides:
    "react native": 3 # boost terms YAKE missed

screen:
  liveness: true # HTTP check — drops filled/expired listings; also backfills descriptions
  liveness_timeout: 8
```

**JobSpy constraint**: On Indeed, `hours_old` is mutually exclusive with `job_type`, `is_remote`, and `easy_apply` — its filter builder is a precedence chain that silently drops the lower-priority filter, so the pass doesn't search what it says it searches. Split into separate search passes to use both. **LinkedIn has no such rule** and is not checked: its builder puts every filter into one params dict and sends them all (retired in #115; both readings are asserted against the installed library by `tests/test_jobspy_contract.py`, and `requirements.txt` pins the version they were read from). An option counts as set only when JobSpy would act on it — `easy_apply: false` and `hours_old: 0` send no filter, so they activate nothing and conflict with nothing. Because `ScraperInput` is a pydantic model that coerces in lax mode, **quoted scalars count too**: `easy_apply: "true"` is a live filter and `is_remote: "false"` is no filter at all, however truthy the raw string looks. `normalize_pass` ([pipeline/sites.py](pipeline/sites.py)) rewrites all four mutex keys to their JobSpy-effective value on the way into a run, before pass selection, kwarg forwarding or the per-row `easy_apply` tag reads any of them. `board_conflicts` normalizes its own input too — the same way it resolves its own boards rather than trusting `cfg["sites"]` — so the scraper, the UI's save endpoint and the example-config guard cannot get different answers by forgetting a preparatory call. A value JobSpy cannot read at all (`easy_apply: maybe`) is reported by `unreadable_options` and skips the pass with a warning, rather than reaching `scrape_jobs` and aborting the stage with a pydantic `ValidationError` after other passes have already scraped. (Worth knowing, since lax coercion is surprising here: `hours_old: true` is not a typo JobSpy rejects, it means *the last one hour*.) The scoping to those four keys is deliberate — the other 12 `OPTIONAL_PARAMS` keys have meaningful falsy values (`distance: 0`, `linkedin_fetch_description: false`) and are forwarded untouched. A pass that breaks the rule **loses the offending board, with a warning**, at scrape time rather than aborting the run — one stale pass no longer takes the healthy ones (in the cloud, the whole day) down with it. The degradation is per board because the rule is (#126): every pass the repo generates names `[indeed, linkedin]`, so `hours_old` plus `easy_apply` conflicts on Indeed and on nothing else, and skipping the pass discarded a LinkedIn search that would have run exactly as configured — verbatim the harm #115 cited, one level up. `resolve_pass_sites` ([pipeline/scrape.py](pipeline/scrape.py)) applies this and the retired-board rule in **one loop over one field** — they answer the same question, and split apart the second had to re-derive the first's answer to subtract from it. It drops the named board and keeps the rest; a pass left with no board is skipped, which is still every single-board case. An *unreadable* value skips the whole pass instead, because `scrape_jobs` builds one `ScraperInput` before it dispatches to any board — no board survives it. **The UI's local-config save still refuses a conflict outright (400)**, for any offending board, and that divergence from the runtime is deliberate: a conflict is repairable while the config is on screen, and splitting the pass costs neither board, where saving it costs the Indeed half for good and says so only in a log line. An unsupported board is warned about rather than refused precisely because it *isn't* repairable. The divergence is one-directional: on **this** rule, everything the endpoint accepts is a config a run acts on exactly as written. (That is scoped to the mutex rule on purpose — an unsupported board saves with a warning and *is* then stripped by the run, which is the same asymmetry seen from the other side.) The reasoning lives at the call site in `pipeline/app/server.py`.

**Supported scrape sites — indeed and linkedin only**: Glassdoor and ZipRecruiter sit behind a Cloudflare wall that 403s every scripted request (they contributed zero rows across months of daily runs), and Google Jobs serves degraded responses then drops the connection mid-body — jobspy's Google scraper doesn't catch that, so one truncated response used to kill the whole run and discard every row already scraped. `resolve_pass_sites` ([pipeline/scrape.py](pipeline/scrape.py)) removes anything else from a config at load time with a warning (protecting stale configs, e.g. an old `SEARCH_CONFIG_B64` cloud secret), and the UI/CLI wizards only offer these two boards.

**Description backfill**: `linkedin_fetch_description: true` makes JobSpy fetch each LinkedIn JD individually during scrape — a sequential per-job HTTP request that easily takes 30+ minutes on 1000 results. Keep it **false**. The screen stage backfills descriptions for the jobs that survive filtering:

- **LinkedIn** URLs are fetched via the public **guest job-posting endpoint** (`jobs-guest/jobs/api/jobPosting/{id}`), not the regular `/jobs/view/` page. The regular page is login-walled from datacenter IPs and inconsistently returns a sign-in preview that has no extractable JD (this caused ~17% of LinkedIn jobs to reach evaluation with an empty description). The guest endpoint returns the full JD reliably and gives a cleaner liveness signal (404 = gone, JD present = live). `linkedin_guest_jd_url()` in [pipeline/screen.py](pipeline/screen.py) does the URL mapping; `job_url` in the CSV stays the human-facing page.
- **Indeed** descriptions usually come from JobSpy directly; if missing, the screen stage extracts them from the same page it fetches for the liveness check (site-specific selectors + a generic `<body>` fallback).

Net effect: we pay ~dozens of fetches per run for the jobs that actually survive filtering, not thousands, and every LinkedIn role gets its complete JD.

## Filtering logic

Keywords are extracted from the resume (`resumes/resume.{pdf,docx,odt}`, no hardcoded vocab):

- YAKE 1–3 gram extraction (weight 1) + explicit Skills-section tokens (weight 2)
- `score_job()` matches keywords against title + description + skills fields
- Target title match → +5 bonus; negative title match → hard-exclude (score = None). An entry is matched **literally** against the title, so one that groups alternatives — `Patient Access / Patient Registration Representative`, `policy or program analyst` — can never fire, and the stage log's `target_titles: N` still counts it; both real wizard-configured copies had every entry in that shape (#160). `setup-profile.mjs` now splits a typed role on ` / ` (with spaces — `UI/UX Designer` is one title) and on a word-bounded `or` (a one-word left side borrows the right side's tail, so `policy or program analyst` becomes `policy analyst` + `program analyst`) before expanding it into queries, and writes **title fragments** rather than the queries into `target_titles` — each split term plus its stem without a generic trailing suffix (`patient access representative` → `patient access`), since a query wants the whole phrase and the bonus wants the part a title keeps (`Patient Access Rep II`). `filter.run` warns once per grouped entry (`_warn_unmatchable_titles`) for configs written any other way. The wizard's Target roles field still reads back the user's own text, from `profile.yml`'s archetypes.
- **A remote claim needs a remote mention** (`filter.remote_requires_mention`, default true; [pipeline/remote_signal.py](pipeline/remote_signal.py)). A board's remote flag is set by the employer's checkbox, not by the JD, so an `is_remote: true` pass returns roles that are plainly on-site in another state — and those rows bypass every location check, because `is_eligible` returns True for a remote row, so each one costs a full evaluation. A row flagged remote (`is_remote`, or `remote_only` — returned by a remote pass and by NO non-remote pass) whose description never mentions remote work is therefore treated as **on-site**: `is_remote` is rewritten to `False` so every later reader sees the truth, and then a `remote_only` row is dropped while any other row falls through to the ordinary location checks. The drop has one exception, and it is the obvious one: a row whose location is one of the user's own non-remote passes' is kept, because a local on-site role is exactly what the local pass exists to find and dropping it because the remote pass got there first would be perverse. Two limits are deliberate. A nearby-suburb row the local pass missed is still dropped — the local pass is radius-bounded and the remote pass is not, so "Plano, TX" under a "Dallas, TX" pass is off-site here; matching is on the pass's city (or a state/country-level pass location) as a whole word, never on the state code, since widening it to the state re-admits the far-away rows the guard exists to drop. And a genuinely remote posting that restricts residency to one state ("must reside in South Carolina") is **not** addressed at all: it mentions remote, so it passes, and its state rule is for the evaluator to read. The judgement is made twice against two states of the same row — filter has the scraped description, and screen re-runs it after backfilling the LinkedIn JDs that arrive empty, re-applying filter's location half through `location_eligible` so a row screen turns on-site meets exactly the checks it would have met had the JD been there. Empty descriptions are left for screen rather than guessed at. Each dropped row is logged `company · title · location` (25 lines, then a count) and written to `output/remote-dropped.csv`; `tests/test_remote_signal.py`, plus `TestRemoteConsistencyGuard` in `tests/test_filter.py` and `tests/test_screen.py`, pin every outcome.
- Jobs sorted descending by `relevance_score`

## Deduplication

Two-stage dedup against the same sources:

- `career-ops/data/scan-history.tsv` (append-only; three statuses, `bridge.SCAN_HISTORY_STATUSES`: `added`, `screened-dead`, `screened-offsite`)
- `career-ops/data/pipeline.md`
- `career-ops/data/applications.md`

**Stage 1 — pre-screen** ([pipeline/screen.py](pipeline/screen.py)): drops URLs already in any of the above *before* HTTP fetches. With 100-result scrapes on a daily cadence ~80% of rows are repeats, so this is the biggest cost saving in the pipeline. Also writes URLs that fail liveness back to `scan-history.tsv` with status `screened-dead`, and rows the remote guard judges on-site somewhere else with status `screened-offsite`, so future runs skip them too.

**Stage 2 — bridge** ([pipeline/bridge.py](pipeline/bridge.py)): catches anything that slipped through (e.g. when liveness is off) and also dedupes `company::role` pairs against `applications.md` so reposted listings under the same role don't get re-evaluated.

`scan-history.tsv` persists across GitHub Actions runs via the workflow's [pipeline state cache](#cloud-automation-github-actions). The first scheduled run creates the cache; from run #2 onward, dedup is active. Cache is per-fork and never committed to git, so dedup state is private even if your fork is public.

**`Discarded` is two things, and only one of them is final** (#163). A person drags a card to Discarded because they decided against the role; the `--recheck-liveness` sweep writes Discarded because a *posting* died. The tracker spells both the same, and every reader treated both as a decision — so when an employer re-posted an opening the re-check had Discarded, stage-2 dedup dropped a same-titled re-post outright (its `company::role` was in `applications.md`), and a re-worded one was evaluated and then folded by merge-tracker's fuzzy tier onto the Discarded row, whose update tier writes score, report, date and notes through but keeps the status. Six rows in a real tracker sat at 4.2–4.8 under Discarded with a fresh report dated after the Discard, invisible to the UI, the work-order and the next re-check. A re-check Discard is therefore **provisional**, and the re-check says so with a `Closed <date> (liveness re-check: <reason>)` mark appended to the row's Notes (`liveness_closed_mark`, [pipeline/_batch_common.py](pipeline/_batch_common.py); the reason is scrubbed of `|` and URLs, which would split the cell or be read back as the posting). Notes, rather than a state file, because the mark then rides along in the cached cloud tracker and through every Refresh — a new cache path would change the cache's version key and orphan every copy's history (see the runtime-state note under Cloud automation). Two readers act on it, and neither touches a Discard a person made: bridge's stage-2 dedup skips a Discarded row carrying the mark, so the re-post is evaluated; and `run_merge_tracker` snapshots the marked rows before the merge (the older merge-tracker replaces Notes on an update; the fork keeps them first) and afterwards resets any whose report number changed to Evaluated with a `Reopened <date>` mark (`_reopen_reposted`), through the same identity-anchored dual-write the re-check uses, so Push carries it to the cloud. The mark rides IN the override (`_override_value`'s `note`) and in the Push payload (`{num: {status, note}}`), and `edit-tracker.yml` applies it through `apply_cloud_overrides` — the repo's own row editor, which replaced the workflow's positional copy — because a status-only Push delivered a re-check Discard to the cloud as a person's, which the cloud never reopens, and the next Refresh (cloud wins verbatim) erased the mark locally as well. The newest mark wins (`closed_by_recheck`), so a person Discarding a reopened row is read as a person. A person's own status write leaves no mark, though, so on a row whose newest mark is the re-check's Closed one the Kanban/report-pane write appends `Set <Status> <date> (by hand)` (`by_hand_note_for`, through the same override+Push channel as the other marks) — that is what makes a later Discard by hand a person's, and re-selecting Discarded on such a row is how a re-check Discard is confirmed as final; an ordinary drag stays unmarked. Because the fork's Notes merge keeps the dead posting's URL first, `extract_url` ([pipeline/app/data.py](pipeline/app/data.py)) now returns the first URL after the last `Re-eval` marker — the posting the row's newest evaluation looked at — else the first URL; the next re-check verifies the live posting and the browser agent is sent to it. Rows Discarded by the re-check before this shipped carry no mark and read as a person's; drag them back to Evaluated once. What this cannot reach: the older merge-tracker *skips* a re-eval that scored lower than the dead posting's, so under it that re-post is lost; the fork the cloud runs writes through in both directions, and `tests/test_merge_tracker_contract.py` drives the higher-score case both accept.

**Three statuses, and only one of them expires.** `bridge.SCAN_HISTORY_STATUSES` is the constant and `append_to_scan_history` raises `ValueError` on anything else — a misspelling would otherwise mint a fourth status that `load_seen` silently treats as permanent, which is the worst of the possible failures because nothing about it is visible. `added` is a role already in the queue or the tracker and `screened-dead` is a posting that is gone; both are forever. `screened-offsite` (written by screen, and only when a career-ops path is given) is different in kind: it is a judgement about the user's own search passes as much as about the posting — the same far-away posting must not be re-fetched every morning, but if they broaden their locations next month it should come back. So `load_seen` takes `expire_days` (`SCAN_HISTORY_EXPIRY`, `{"screened-offsite": 60}`) and stops counting those lines as seen after sixty days; a line whose date cannot be parsed is treated as permanent, the stricter reading. The pre-screen dedup treats ANY status as seen, which is what makes the expiry the only route back for an off-site row — that, or deleting the lines by hand. Pinned by `TestScanHistoryStatuses` and `TestScanHistoryExpiry` in `tests/test_bridge.py`.

**`screened-dead` is permanent** — no run ever re-checks a URL carrying it — so only a verdict that a posting is *gone* may produce it. So **`expired` requires positive evidence** — a 404/410, an error redirect, a closure banner, or a listing page we landed on instead of the posting. `classify_liveness` ([pipeline/screen.py](pipeline/screen.py)) resolves *everything else* to `throttled`/`uncertain`, including the catch-all fallthrough, which used to be `expired`. That inversion is the point: 5xx, a 200-served bot wall and upstream's `redirected_off_posting` were all the same failure reaching the same branch, so requiring evidence retires the class instead of naming its members one at a time — the next thing upstream learns costs a re-fetch, not a role. Holding is bounded by the scraper: a held URL never enters scan-history, so it is re-checked only while the search still returns it. A `throttled` verdict is further split by `transient_throttle`: a limiter or an upstream API outage may clear, so the re-check leaves the role's timestamp unset and it returns to the front of the stalest-first queue; a wall, a 5xx or an unreadable body will not, so it is stamped and rotates through the normal cadence instead — still never expired, but not ahead of every other role forever, which would let `RECHECK_BUDGET` of them consume every run. The cases that reach the non-fatal side: a 403/429/999 wall (decided on status, before the body is touched), a **5xx** (the site is broken, not the posting removed), a **200-served anti-bot challenge** (Cloudflare "Just a moment…", hCaptcha — the status check can't see these), and any body too short to judge. The bot-challenge patterns are matched against the whole page, JD prose included, so they run *after* the apply-control check and are spelled to need Cloudflare's own wording — a false positive holds the row on every run, meaning the job is never evaluated at all. Upstream's `liveness-core.mjs` grew the same guard for the same reason; `screen.py` is a port of it, and a port drifts.

## The career-ops contract

career-ops is a separate upstream project on its own release cadence, and the pipeline reads, writes and executes files inside it. What that costs us, and the shape of each defence:

- **`node merge-tracker.mjs` needs `npm install`.** It used to import only Node builtins; it now reaches `js-yaml` via `tracker-utils.mjs`. A career-ops checkout updated with a bare `git pull`/rebase fails to resolve it, and `run_merge_tracker` catches that as a non-fatal failure — so evaluations pile up unmerged in `batch/tracker-additions/`. It prints an actionable hint on `ERR_MODULE_NOT_FOUND` rather than the raw stack.
- **Exit 0 no longer means "everything merged".** merge-tracker declines a row it can't read confidently (see the score cell below, or a report number marked `failed` in `batch-state.tsv`) by printing `Skipping …` — and then still archives the TSV into `merged/` and exits 0. Nothing retries it. `run_merge_tracker` compares the additions it saw pending before the merge against what actually reached the tracker afterwards — an addition that left `tracker-additions/` without landing in `applications.md` is lost — and prints merge-tracker's own reason lines alongside, read from **stdout and stderr**: every refusal but one is a `console.warn`, so reading stdout alone printed nothing on a real loss and could only ever surface the one refusal logged to stdout, which is the benign unscoreable-re-eval case belonging to some other row. Asking the filesystem rather than grepping upstream's prose is deliberate: those messages come in half a dozen phrasings and at least one of them is benign (a re-eval that produced no score keeps the row's existing score), so a `Skipping` grep cried wolf on intact rows. **"Did it land" has two readings, and the check needs both** (#152). merge-tracker matches an addition against the tracker on four tiers, and on the two *guessed* ones — entry number, fuzzy title — it updates the row but keeps THAT ROW's title, so a fuzzy false positive can't also erase the evidence that two reqs were distinct; its own `🔄 Update` line prints the *addition's* title, so the substitution is invisible there too. Keying on `company::role` alone therefore reported three intact evaluations as lost on a real run, while their report links and scores had written through exactly as intended — and a guard that fires on intact rows camouflages the loss it exists to catch. A row now counts as landed under `company::role` **or** under company + report number, which is what those tiers do preserve. Each key covers the other's blind spot: an unscoreable re-eval is skipped with the row's existing report left standing, so only the first can see that one. Landing under the report number alone gets its own (non-warning) line, because it is the one place the retitle is visible — the fold may have collapsed two genuinely distinct reqs, and from then on only one title is the `company::role` the rest of the pipeline keys on (bridge's stage-2 dedup, handoff's `role_key`, the résumé-base picker). The whole second reading rests on one ternary in a file that changes on a `git pull`, so `tests/test_merge_tracker_contract.py` drives the real `merge-tracker.mjs` and asserts it — local-only, skipping without a checkout and npm deps, the same shape as `TestNodeRoundTrip`.
- **The score cell must be exactly `N/5`.** merge-tracker decides which of columns 5-6 is the score by asking whether exactly one of them looks like one; when neither does it skips the row. `_normalize_score_cell` ([pipeline/_batch_common.py](pipeline/_batch_common.py)) coerces the model's output on the way out — an out-of-range value becomes `N/A` rather than being clamped, because the handoff work-order ranks by score and a fabricated 5 would put the role first. The older merge-tracker's fallback assumed this row order, so the prompt's "format X.X/5" rule was advisory; it is load-bearing now, and a prompt rule is not something a local model reliably honours. **And `write_job_result` is not the only writer.** `--batch` routes through career-ops' `batch-runner.sh`, which owns `tracker-additions/` and lets the agent CLI write each TSV directly, never entering Python — so those rows reached the merge with none of the chain applied, and a bare `4.2` cost the evaluation outright (`tests/test_merge_tracker_contract.py` drives the real script to prove the refusal, the archive, and the exit 0 that hides it). `sanitize_addition` is therefore applied a second time by `run_merge_tracker`, over every pending TSV on disk — **for the merges we run**: `--evaluate-batch`, the UI, and the heal sweep. A `--batch` run needs one more step, because `batch-runner.sh` calls `node merge-tracker.mjs` itself as its last act with no Python in the process tree, so a row the agent CLI wrote with a bare `4.2` is refused and archived into `merged/` before anything here sees it. `run.sh`/`run.ps1` therefore run `python -m pipeline.merge_additions` after the runner returns, and `run_merge_tracker` begins with `_recover_refused_additions`: it applies the loss guard's own two-reading "did it land" test to every archived row and re-queues the ones that did not — **but only when the score fix would change the row**, since an unreadable score is the one defect that gets a row refused. That rule is load-bearing twice over: a row refused for a reason we cannot cure (a report number marked `failed`, which upstream refuses on purpose) would otherwise be re-queued and refused again on every run, and a row the user *deleted* from the tracker merged with a readable score, so it can never qualify to come back. `tests/test_merge_tracker_contract.py` drives the refusal, the recovery and the second merge against the real script. That is one chain applied at two points rather than two mechanisms, which is only possible because the chain is **idempotent** (`tests/test_batch_common.py` pins `sanitize(sanitize(x)) == sanitize(x)` over the row shapes it meets). Two rules there are load-bearing and easy to get wrong, because each was. **Which rows the chain touches is decided by one classifier**, `_row_parts`, anchored on the Report cell rather than on a width: career-ops' worker writes "9 columns plus a trailing `url`", so `== 9` skipped the score fix on those rows while the unguarded pipe strip still rewrote them (a repair counted and logged over a row still refused), and `>= 9` then mangled a row with an *early* extra cell into a shape merge-tracker accepts — turning a refusal the loss guard reported into a silently merged garbage row. And it **reads the file without `read_text`'s strip**, which eats the trailing tab of an empty Notes cell and made a correct row look one cell short — re-padded, rewritten and counted as repaired on every merge. What a foreign row has lost is recovered by job id — the addition's own filename, for our writers and career-ops' batch prompt — with the row's own trailing URL as the fallback; a `{num}-{slug}.tsv` row finds nothing and keeps the score repair, which is the one that decides whether it merges at all. The rest of the mechanics live on `_sanitize_pending_additions`.
- **A req id in Notes is what keeps two same-titled openings apart.** merge-tracker's fuzzy tier compares titles through `role-matcher.mjs`, which drops tokens of three characters or fewer before matching. Until career-ops#3651 (merged upstream 2026-09-02) that made `INSURANCE SPECIALIST I` and `INSURANCE SPECIALIST II` one opening; a checkout that has pulled it treats a level stated on both sides as a disagreement, so two levels no longer fold — but `PACT PRN Representative I` and `PACT Representative I` still do (the `PRN` — as-needed staffing, a different employment arrangement — is discarded as noise), and so do two genuinely different requisitions whose titles differ only in a suffix the matcher ignores. A fold keeps the existing row's title, and the second requisition stops existing: invisible to bridge's stage-2 dedup, handoff's `role_key`, the résumé-base picker and the UI. Measured on a real 316-JD corpus, the req-id route reaches few of these — 5% of postings state an id, and none of the ten pairs that would fold carried one on both sides (#157, closed on that) — so it is kept because it costs nothing and its precision held, not because it is the fix; the level rule upstream is. `tests/test_merge_tracker_contract.py` uses a re-worded pair (`… II` vs `… II (Remote)`) precisely so it holds on a checkout on either side of #3651. career-ops documents the remedy — a req/job/posting id in the **Notes** column, which `REQ_NUMBER_RE` reads and treats as proof two rows are distinct — so `extract_req_id` ([pipeline/_batch_common.py](pipeline/_batch_common.py)) pulls one from the cached JD and `_inject_req_id_into_notes` writes it as `req <id>`, a form upstream's `REQ_NUMBER_RE` reads back. Not always *unchanged* — that regex's own capture excludes `_`, so a Taleo-style `R_1488728` comes back as `1488728` — which costs nothing, because both sides of the comparison are cells we wrote the same way. An id it cannot parse at all degrades to no id on one side, and the guard needs both, so it fails safe rather than splitting. A row carries one when a merge this repo runs sees it pending AND its JD is cached under the addition's job id (see the sanitizing rule above); a `--batch` run merges its own rows first, and a `{num}-{slug}.tsv` addition has no JD to read one from, so those still fold. Three rules are load-bearing. It is the **employer's** id, never the board's `jk=`/`currentJobId` key: that identifies a POSTING, so a re-post of one requisition carries a new one and keying on it would add a tracker row every time a listing is re-published (both directions are pinned in `tests/test_merge_tracker_contract.py` against the real script — different ids must split, the same id must still fold). The same objection reaches the other tempting route — giving the tracker a URL column so merge-tracker's Pass 0 can match — though less far than it first appears, so the size of it is worth stating exactly. Bridge already drops an addition whose lowercased `company::role` is in the tracker ([pipeline/bridge.py](pipeline/bridge.py)), so an *identically* titled re-post or second-board copy never reaches the merge at all. What the fuzzy tier still folds is therefore titles that differ in text but not in meaning: one opening whose title picked up a suffix on re-posting, or the other board's wording of it. Folding those is a feature, and **any per-posting key splits them** — `jk=`, `currentJobId`, or the URL itself via `urlBlocksHeuristic` — where an employer's req id does not, because it is the same id on both boards and across re-posts. That is a narrower objection than "it splits every cross-board pair", and it is the real one. The extractor reads the format the cache is actually written in — JobSpy's `description_format` defaults to MARKDOWN, so an Indeed JD arrives as `**Job ID:** 88214` with `_`/`-` backslash-escaped mid-word, while LinkedIn's is backfilled as plain text by screen.py; a pattern written for prose worked on one board and silently never fired on the other, which is worse than failing on both. It is also **stricter than the regex it feeds**: upstream accepts a bare `job`/`req`/`ref` label because a human wrote that cell and meant it, while a JD is thousands of words we did not write, where "job 2 of 5" is ordinary — so a label here must carry an explicit id/number qualifier, and several *different* ids in one JD resolve to none rather than a guess. And the id leads the cell, ahead of the URL, because `extractReqNumber` takes the first match: today's posting URLs yield no match at all (pinned by a test), but that is a property of current URL shapes, not a promise about the next board. Only new rows carry an id, so a pair already folded on disk stays folded.
- **The Report cell is model-authored, so the writer overrides it.** The prompt gives the model only the link's SHAPE, `[N](reports/N-company-slug-DATE.md)`, and it invents the slug — keeps an `&`, appends the role, uses an en-dash — while `write_job_result` names the file by its own slug. Six of 230 rows in a real tracker linked a file that never existed (#162). The UI never noticed, because `find_report_file` resolves by number; the readers that resolved `career_ops / report_path` — cover letters and both tailors — got `""` from `read_text` and built from the JD alone, with no log line. So `sanitize_addition` grew a `report_file` step: `write_job_result` passes the file it just wrote, and the merge-time pass (`_dead_link_repair`) looks a DEAD link up by its number and leaves a live one alone, whichever relative shape it has, since the link is the one cell that knows which of two same-numbered files the row meant. Rows already merged keep the link they were merged with, so the three readers now go through `read_report`, which resolves the same way and prints one line either way. `find_report_file` (and the lock-vs-report rule below) therefore lives in `_batch_common.py`; `app/data.py` re-exports it.
- **Report links come back as `../reports/…`.** merge-tracker normalizes the Report cell relative to the tracker file, which the pipeline seeds at `data/applications.md`. Both shapes coexist in one file (older rows were copied verbatim). `_report_link` ([pipeline/_batch_common.py](pipeline/_batch_common.py), imported by the UI's parsers) strips the ascent at the single point both parsers extract it, so the three consumers that resolve it as `career_ops / report_path` — cover letters and both tailors — keep finding the report instead of silently building from the JD alone.
- **The tracker has two layouts.** career-ops supports an optional `Via` column (the agency a role comes through) after Company, migrated in with `merge-tracker.mjs --migrate-via`; its own readers map columns by header name. So do ours now (`_header_columns`, and the same anchoring in [pipeline/bridge.py](pipeline/bridge.py)), falling back to the positional order for a headerless table. Read positionally the extra cell puts the agency where Role belongs, and `company::role` is the key bridge dedup, handoff's `role_key`, the résumé-base picker and the tailored role all run on.
- **What career-ops ships as DATA is read, not mirrored.** Two contracts arrive as machine-readable files and both are loaded at runtime, cached per (path, mtime), with the baked constant as a fallback for when the checkout is absent (`run-ui.sh --data` points the UI at an extracted artifact): `templates/states.yml` → `canonical_states()`/`canonical_status()` ([pipeline/app/data.py](pipeline/app/data.py)), and `tracker-aliases.json` → `header_aliases()` ([pipeline/tracker_layout.py](pipeline/tracker_layout.py)). A 10th state now reaches the Kanban, the report-pane picker and `/api/status`'s validator with no code change — `app.js`'s `STATES` is a first-paint seed that `/api/capabilities` replaces at boot. This is the lesson of the v1.29.0 rebase written down: the hand-mirrored alias table was wrong the day it was written (missing `location`, `materials` and `apply link`; inventing eight Spanish spellings career-ops never emits), and `Hired` broke the status mirror the same week. A copy of a file that sits on disk is a bug with a delay on it.
- **`NNN-RESERVED.md` in `reports/` is a lock, not a report.** Newer career-ops reserves a report number by dropping a sentinel file whose body is JSON (`{"pid","token","created_at"}`), replaced by the real `NNN-company-date.md` when the worker finishes — and left behind whenever a run is killed first. It carries the same `NNN-` prefix our readers key on, so the two questions asked about a report number now need opposite answers: `find_report_file` ([pipeline/_batch_common.py](pipeline/_batch_common.py), re-exported by `app/data.py`) resolves a number *to a file to render* and must SKIP locks, or the UI's report pane renders raw JSON where the evaluation belongs; `max_report_num` ([pipeline/_batch_common.py](pipeline/_batch_common.py)) and `_report_numbers` ask *is this number taken* and must COUNT them, or Add-Job hands out a number career-ops just reserved. Both sites say so at the call site, because "make them consistent" is the tempting wrong move. Worth knowing that the vendored checkout can lag this: the copy in this repo (v1.8.1) has no `reserve-report-num.mjs` at all and reserves inside `batch-state.tsv`, so the convention is pinned from a newer upstream than the tree — a `git pull` in career-ops changes which behaviour you get.
- **`## Pendientes` is our spelling, not the only one.** career-ops writes the pending/processed headings in English and reads both; bridge matches whichever the file already uses, so it appends into the existing section instead of opening a second one.
- **`npm install` runs a Chromium download.** career-ops ships a `postinstall` of `npx playwright install chromium --with-deps`. Every install site here passes `--ignore-scripts`: `setup.sh`/`setup.ps1` install Chromium deliberately further down (and the Nix path needs a pinned version, not whatever postinstall fetches), and the daily workflow only ever shells out to `merge-tracker.mjs`, so it would be minutes of runner time plus a sudo-dependent apt step for a browser nothing there launches.

## Interactive batch evaluation (`--batch`)

Invokes `career-ops/batch/batch-runner.sh` with the CLI [pipeline/agent_cli.py](pipeline/agent_cli.py) resolves — `BATCH_CLI` from `.env`, else `DEFAULT_CLI`. `run.sh`/`run.ps1` ask for it (`--resolved`) rather than defaulting themselves, because `.env` is where the Setup wizard writes the answer and a shell wrapper cannot read it. The CLI agent runs fully locally — it reads files, calls WebSearch, generates PDFs.

Key options forwarded to the runner:

```
--cli <id>                         from `--resolved` (BATCH_CLI, else the registry default)
--model <name>                     OLLAMA_MODEL, else `--resolved-model` (AGENT_MODEL, else
                                   the CLI's registry default); omit both for the CLI's own
--skip-pdf                         skip PDF step (report + tracker only)
--min-score N                      skip tracker for jobs scoring below N
--retry-failed                     re-attempt failed jobs
--dry-run                          list pending without processing
--start-from N                     resume from job ID N
```

State persisted in `career-ops/batch/batch-state.tsv` — safe to interrupt and resume.

## Multi-provider evaluation (`--evaluate-batch`)

Evaluates jobs synchronously using any LLM provider. Results are immediate — no async wait.

**Protected characteristics never reach an evaluation prompt** (#165). The wizard collects EEO self-ID answers (gender, race/ethnicity, veteran and disability status) so the *browser agent* can fill them on an application form, and `setup-profile.mjs` writes them into `profile.yml` under `voluntary_disclosures:` — which `build_system_prompt` embedded **verbatim**, so every evaluation saw them. Two separate harms, and only one is about privacy: a model that scores job fit must not see the characteristics a fitness judgement is forbidden to rest on, which holds on a paid tier and with consent; and on a free provider tier those answers may additionally be retained. Redaction sits on the **read**, not on one builder: five prompt builders in this repo eat the candidate files, so a sixth would be safe only if its author remembered — `profile_yml_for_prompt` / `profile_master_for_prompt` are the sanctioned accessors, and `tests/test_batch_common.py::TestNoUnredactedProfileReads` fails on a raw read unless the exact source line is listed with a reason (keyed on the LINE, not the module, since `skills.py` and `handoff.py` each hold both a safe read and a prompt read). Two builders were leaking the same data and are now fixed: `skills.build_tailor_messages` pasted the whole `profile.yml` into the API résumé-tailoring prompt, and `resume_content.generate_for_job` read `PROFILE.md` raw as the build's ONLY source of truth. Both routes in need separate passes because they are different formats. `redact_profile_yml` ([pipeline/_batch_common.py](pipeline/_batch_common.py)) drops the whole `voluntary_disclosures:` section on the seed path — the whole section, not just the four EEO keys, since the rest is the site-consent booleans (`data_processing_consent` / `save_answers` / `share_answers`), apply-path form data an evaluator has no use for. `redact_profile_master` drops the `- **Label:** value` standing-answer bullets on the `PROFILE.md` path, matched by **word-anchored** stems (`\b(gender|race|ethnic\w*|veteran|disab\w*)`) rather than exact labels — the file is agent-grown and append-only, so an exact allowlist misses "Gender identity", while an UNanchored stem eats the fact-bank bullets for "Grace Health" and "Terrace Senior Living" and silently deletes real experience from the résumé it is about to write, which needs its own pass precisely because that file SUPERSEDES the seeds when present AND is non-clobber, so an install seeded by an older version keeps those bullets forever and no regeneration removes them. Both are line-based rather than `yaml.safe_load` + dump: `_batch_common` is stdlib-only on `sites.py`'s terms, and a round trip would reorder keys and drop comments in a document otherwise passed through verbatim. A column-0 comment inside the section is dropped **with** it rather than ending the block, the conservative read. `render_profile_md` no longer seeds the four fields at all — a new `PROFILE.md` carries an instruction to decline or choose "prefer not to answer" where the form offers it and to record `handoff` where a form requires a value, so the person answers it themselves. `profile.yml` still holds whatever the wizard was told: it is the person's own record, and the fix is that it stops reaching the model, not that it stops existing. What this cannot reach is a hand-written `PROFILE.md` that states a protected characteristic in prose rather than in the generator's bullet shape; that is the user's to edit. `tests/test_batch_common.py::TestProtectedCharacteristicRedaction` pins both paths, the comment case and idempotence.

**Candidate profile source:** when a living `PROFILE.md` exists (handoff dir, else `career-ops/PROFILE.md` — see `resolve_profile_md`), it is the authoritative candidate profile fed to the evaluator, superseding the `cv.md`/`profile.yml`/`_profile.md`/`article-digest.md` seeds. The batch path and the UI's Add-Job eval share one builder (`eval_system_prompt`), so they resolve it identically. Absent a PROFILE.md, the four seeds are used as before. The cloud daily reads it too when the optional `PROFILE_MASTER_B64` secret is set — the Setup wizard encodes your living PROFILE.md and the workflow decodes it to `career-ops/PROFILE.md` (`resolve_profile_md`'s fallback); without the secret, the cloud uses the seed secrets exactly as before.

```powershell
./run.ps1 --evaluate-batch                         # auto-detects provider from env keys
./run.ps1 --evaluate-batch --batch-provider gemini # explicit provider
./run.ps1 --evaluate-batch --batch-concurrency 5   # more parallel workers
```

Provider auto-detection order: Gemini → Groq → DeepInfra → OpenRouter → DeepSeek → OpenAI → Anthropic (first env key found).

| Groq | `GROQ_API_KEY` | Yes — fast open-source models |
| DeepInfra | `DEEPINFRA_API_KEY` | No — pay-as-you-go open-weight models |
| OpenRouter | `OPENROUTER_API_KEY` | No — pay-as-you-go, many models via one key |
| DeepSeek | `DEEPSEEK_API_KEY` | No — pay-as-you-go, cheaper than frontier |

Set in `.env` or as repository secrets for GitHub Actions. `BATCH_PROVIDER` overrides auto-detection.

**Gemini rate limits are the user's to supply** ([pipeline/gemini_limits.py](pipeline/gemini_limits.py)). There is no API that returns a project's limits — Google's rate-limits doc no longer prints per-model numbers at all, deferring to AI Studio's login-gated `/rate-limit` page — so `GEMINI_FREE_TIER_LIMITS` is a hand-copied snapshot that is wrong twice over the moment Google moves: stale for the free tier, and never right for a paid one, where the same IDs carry different numbers. It is therefore the **fallback**, not the source. `config/gemini-limits.json` (gitignored, `GEMINI_LIMITS_FILE`) holds the user's own numbers and wins per model, read at runtime and cached on mtime — the same "read the data, don't mirror it" shape as `canonical_states()` and `header_aliases()`, and for the same reason. A malformed file degrades to the table and one bad row never costs the user the others. What the table *can* self-check is IDs: `python -m pipeline.gemini_limits --check-models` diffs them against `models.list` (which carries no limits, and says so, or a clean run would read as "the numbers are verified"); `--show` prints what is in effect and where each row came from. The load-bearing part is that conforming is keyed on **membership**: a model Google added after the snapshot got no pacing, no cap *and* no warning, so ticking "I'm on the free tier" bought silence rather than conformance — `format_unconformable_warning` is that case made audible, and `tests/test_gemini_limits.py` pins the precedence, the degradation and the silence-turned-warning. Conforming acts on all three published limits, which are not the same kind of thing: RPD is a **quota**, so `cap_to_rpd` slices the run to it and defers the rest; RPM and TPM are **rates**, so both pace inside `paced_caller` and the lower of the two is what a run actually achieves. TPM was stored, printed and collected by the wizard but read by nothing until #143 — harmless while the table claimed the Gemma pair had unlimited TPM, and a 429 on a quota nothing warned about the moment a real 16,000 landed there: at a ~9,500-token call, that row's 30 RPM is 15x what its token budget can pay for, and it is the row `batch_recommendation` steers batch users toward. `TokenBudget` is a rolling window rather than a second `RateLimiter` because a request's cost varies — one 8K-token call can eat half the minute — so it schedules the next charge at the first instant the oldest has aged out far enough to make room, and keeps that schedule non-decreasing (FIFO, and it is what makes checking one window per charge sufficient). A failover chain is paced **per member**, inside the chain (#147): `_build_failover_caller` wraps each member's caller with `paced_caller` as it builds the chain (a no-op for a model outside the free-tier table), so the request that actually goes out is paced to the row of the model it goes to — pacing the whole chain on its lead's row held the documented `gemini-2.5-flash,gemma-4-26b-a4b-it` chain's fallback (16K TPM) to flash's 250K budget, 15x over, for the whole run once flash's 20 RPD were spent, and charged N real attempts to the lead as one prompt. And the pacer's queue wait is **credited back to the per-job deadline** (#148): `TokenBudget.acquire`/`RateLimiter.acquire` return what they slept, `paced_caller` records it per thread, and `_call_with_retry` takes it on each failure and extends the deadline — `LLM_JOB_BUDGET` is about how long the *provider* may take, and a worker that queued nine minutes on our own token budget used to meet a transient 429 with a retry loop that gave up on attempt 1, exactly where the soft token estimate relies on the backoff. The limiter and budget are keyed on the **model**, not held per caller: the UI builds a fresh caller per Add-Job request thread and per résumé-tailoring call, and per-caller state hands each of them the model's whole budget — close to invisible under RPM alone, a guaranteed doubling against a 16K TPM the eval path is designed to saturate. (`handoff.py` carried that rule as a comment on one call site; keying it on the model makes it a property of the module.) The prompt is measured in the wrapper rather than passed in (every caller in the repo is `(system, user)`, so the whole prompt is already in hand) at ~4 chars/token; the response is charged as a reserve and corrected upward once it arrives, since TPM counts both directions and reserving `MAX_TOKENS` would halve throughput to insure against a size responses don't reach. The estimate stays approximate on purpose — `_call_with_retry` still backs off a 429, whereas an exact count is a network round trip per call on the path that exists to spend fewer of them. The same correction runs through the reporting, or the run would pace to one number and promise another: `_row_capacity` is the lowest of all three limits expressed as evaluations/day (`_capacity_terms` spends each rate over 1,440 minutes) — all three, because the baked table hides the general rule behind RPD binding on every row, while a user's own numbers reach combinations it never had, and a 1 RPM row is 1,440 a day however large the quota beside it. That figure is what the warning quotes, what `--show` flags a rate-bound row with, and what `batch_recommendation()` ranks by — it replaced a baked constant chosen by highest RPD, which is the wrong selector precisely when TPM binds. `free_tier_viability`'s `exceeds` moved onto that capacity while `cap_to_rpd` stays on the quota: exceeding a quota gets requests refused, while exceeding a rate only makes the run long, and deferring work to a tomorrow with no more tokens per minute than today buys the user nothing.

## Cloud automation (GitHub Actions)

> **Privacy first**: every cloud workflow refuses to run unless your fork is private. The Actions tab of a public repo exposes workflow run history, schedule cadence, and durations — all of which reveal active job searching. See the privacy notice at the top of [README.md](README.md).

Cloud automation workflows:

| Workflow | Schedule | What it does |
|----------|----------|--------------|
| `daily-pipeline.yml` | Noon UTC (7 AM CDT) | Runs **every** search pass (including any `easy_apply: true` pass) once a day — no pass-selection flag. Scrape → filter → screen → bridge → evaluate → **digest**. Its first step records `date +%s` (`id: started`) before the checkout, so the clock starts where billing does; the evaluate step carries `id: run` so the digest can read its `outcome`. |
| `gc-actions-storage.yml` | Sundays 03:30 UTC | Garbage-collects the two things that consume the account's Actions **storage** quota: artifacts beyond the newest N *per artifact name*, and workflow **run logs** older than 30 days (retention settings don't cover logs at all, and nothing else here removes them). Skips in the template repo; no private-repo hard-stop, since pruning your own storage exposes nothing. `workflow_dispatch` takes `keep_artifacts` / `log_retention_days` / `dry_run`. |
| `export-reports.yml` | Manual (`workflow_dispatch`) | Packages the **full** `career-ops/reports/`, plus the current `data/applications.md` the Report links resolve out of, from the state cache as one downloadable artifact — the recovery path the per-run daily artifact removed (a fresh local install gets the whole tracker but only the last run's report files, so every Report link would 404). Restore-only, so unlike `seed-reports.yml` it's safe to run while a pipeline is in flight — which is why it's the one pipeline-state workflow with **no** `concurrency:` block (see the runtime-state bullet below). Dispatch-only on purpose: `tests/test_workflow_artifacts.py` forbids a **scheduled** upload from naming cached state, which is exactly the bug, but a human asking for the history once is bounded by the asking. Both path entries are load-bearing: `upload-artifact` roots the archive at the common ancestor of the paths it is given, so naming only `reports/` would re-root it and the download would stop extracting over a local `career-ops/`. |
| `edit-tracker.yml` | Manual (`workflow_dispatch`) | Replaces `applications.md` in the cache with a user-supplied base64 blob. Use after editing the tracker locally. |
| `update-from-template.yml` | Mondays 04:00 UTC **when opted in**, or manual (`workflow_dispatch`) | Merges the upstream template's latest `main` into this copy and pushes (copies have no fork link). Skips in the template repo itself; aborts on conflict. The weekly schedule proceeds only when the repository variable `AUTO_UPDATE_FROM_TEMPLATE` is exactly `'true'` — the Setup wizard's "Keep my copy updated weekly" box sets it — while a dispatch always proceeds: a merge lands in the copy's history unasked, so it is opt-in rather than default. `tests/test_template_update_flag.py::test_scheduled_runs_are_var_gated` pins the gate. The UI's **⬆ Update** button does the same merge+push locally (also refreshing the clone running the UI); `pipeline/app/self_update.py` holds the logic. |

**Storage model — no user data is ever committed:**

- **Setup data** (CV, profile, search config) → repository **Secrets** (encrypted at rest, not visible to forkers)
- **Runtime state** (scan-history, applications.md, pipeline.md, recheck-state, batch state, cached JDs) → **`actions/cache`** keyed `pipeline-state-v1`. Per-fork, restored at workflow start, saved at workflow end. Invisible to anyone but the fork owner. **Three workflows write it** — the daily, `edit-tracker.yml` and `seed-reports.yml` — and a save is a *whole snapshot*, not a merge, so two overlapping writers mean the later save wins outright and the other run's work is gone unannounced. All three therefore share the `pipeline-state` **concurrency group**; the daily sat in a group of its own until #135, which left that the one writer race nothing serialized and nothing documented (the UI's **Push** dispatches `edit-tracker.yml`, and the noon daily is long). A Push dispatched mid-daily now queues behind it. The serialized window is a writer's *whole run*, not its save step — each one restores at the start and saves at the end, so a save landing anywhere in between is overwritten. `export-reports.yml` is the deliberate exception: it restores and never saves, and a restore matches a complete, immutable entry and can clobber nothing, so joining the group would buy no safety and would make the recovery path queue behind the very run you're recovering alongside. The cost of the group is GitHub's **one pending run per group** rule — dispatch a second writer while one is queued and the queued one is cancelled. That bites hardest on Push, because `/api/push-status` clears a pending override the moment the dispatch is accepted, so an evicted Push loses those status edits from the cloud and pressing Push again sends nothing; re-drag the cards if a queued **Edit Tracker** run turns up cancelled. Worth taking: a cancelled run is visible in the Actions tab, a clobbered cache is visible nowhere and costs a day's evaluations, reports, scan-history rows and batch state.
- **Outputs** (**this run's** new reports + the current tracker) → **`actions/upload-artifact`**. Downloadable from the Actions tab for **7 days**. Both halves are load-bearing, and each is useless alone: `career-ops/reports/` is restored from the state cache every run and only grows, so uploading it whole put the entire report history into *every* artifact — and retention bounds how MANY artifacts are alive, never how big each one is. Ninety days of a monotonically growing directory made live storage grow with the *square* of how long the pipeline had run, which exhausted the account's Actions storage; an exhausted storage quota stops GitHub creating workflow runs at all, including the Tests run on every PR, and nothing in the Actions UI connects the two. So the daily now snapshots `reports/` right after the cache restore and uploads only what the run itself minted ([pipeline/run_artifact.py](pipeline/run_artifact.py)). `data/pipeline.md` and `data/easy-apply-urls.txt` no longer ride along either — both are append-only and nothing read them out of the artifact, so they reproduced the same shape at a smaller constant. What's left that grows is `applications.md`, which is irreducible: the UI's **↻ Refresh** *merges* the tracker, so a diff of it would be useless, and a row is ~200 bytes against ~4KB for a report. The artifact keeps career-ops' layout, so the Refresh merge is unchanged — it just accumulates the history into your local `career-ops/` a run at a time, and **Export Reports** pulls the whole backlog down in one go when that isn't enough. `tests/test_workflow_artifacts.py` guards the retention ceiling, the classification of every cached path, and the rule that no *scheduled* upload names cached state. It also guards the rule the cache itself rests on (#133): **every** workflow's `actions/cache` restore/save must name the same path set and the same key prefix as the daily's. GitHub hashes the path set into the cache *version* and matches a restore on prefix AND version, so a workflow whose list has drifted does not restore less — it matches nothing and silently starts a lineage of its own. `export-reports.yml` shipped naming two of the nine paths and so never restored anything; `seed-reports.yml` named seven and spent months repairing into a cache the daily never read. And the same rule from the other side (#135): every workflow that **saves** the cache must run under the `pipeline-state` concurrency group, and none of them may set `cancel-in-progress: true` — every save step is `if: always()`, which fires on cancellation too, so cancelling a daily mid-run would write its half-evaluated batch state and partly-merged tracker over the good snapshot on the way out. Anything under `actions/cache` that isn't explicitly the `restore` half counts as a writer, so a paste of the combined `actions/cache@v6` action fails the rule rather than escaping it.
- **Delivery** (what the run found) → a Discord message and/or an email, sent by the "Send the daily digest" step ([pipeline/daily_digest.py](pipeline/daily_digest.py)) immediately after the evaluate step and before the cache save, `if: always()`. It is the only part of the cloud loop that reaches the person without them going and looking, so it is deliberately placed where a *failed* run still reaches it, and it exits 0 whatever happens. It READS cached paths (`career-ops/reports/`, `data/applications.md`) and writes nothing under them: the artifact guard forbids a *scheduled upload* of cached state, and a read is not that — said in a YAML comment above the step, since "names a cached path" is what the guard greps for. Its `--root` and `--manifest` must equal the snapshot step's, because that pair is the whole definition of "this run's reports", and `tests/test_workflow_env.py` asserts it along with every env name, derived from `daily_digest.SECRET_VARS`/`SETTING_VARS`/`RUN_VARS` rather than restated.
- **Every job declares `timeout-minutes`.** GitHub's default is 360 and the Free plan is 2,000 Linux minutes a month per ACCOUNT, so one hung LinkedIn scrape at the default is 18% of the month, spent on nothing. The daily's evaluate job gets 150 and every other job in the repo gets 30 (the daily's preflight, 10). The daily's number sits deliberately ABOVE the real run length rather than at the budget: conforming to the free tier's recommended row paces 160–190 evaluations to ~95–115 minutes on their own, and a timeout cancel does not defer those evaluations, it loses them — the batch exits before the merge and `tracker-additions/` is not cached. The budget is guarded by the digest's health line, which quotes the run's minutes and their ×30 projection, not by this clock; lowering the ceiling below a real run is a decision to throw evaluations away. `tests/test_workflow_env.py::TestEveryJobHasAClock` holds all three rules.
- **Free-tier conformance is a cloud setting too** (#143's mechanism, wired to the cloud). The evaluate step carries `GEMINI_FREE_TIER: ${{ vars.GEMINI_FREE_TIER || '' }}` and `GEMINI_LIMITS_FILE` pointing into `runner.temp`, and a preceding "Write Gemini limits" step writes the `GEMINI_LIMITS_JSON` repository variable verbatim to that path when it is non-empty — under `RUNNER_TEMP`, so the user's own AI Studio numbers are neither cached nor checked out, and a malformed value degrades to the built-in table by `gemini_limits`' own rule. The re-check's `RECHECK_BUDGET` / `RECHECK_MIN_AGE_HOURS` are wired the same way, as `vars.NAME || ''`: both are read through `env_float`, which returns the code's default on an empty string, so the workflow states no number of its own and cannot drift from one. Without either variable the cloud behaves exactly as before.

**Pass selection flags** (mutually exclusive, for manual/local runs): `--only-pass "name1,name2"` (case-insensitive name match, errors on no match), `--easy-apply-only` (passes with `easy_apply: true`, no-ops if none), `--no-easy-apply` (passes without `easy_apply: true`). The daily cloud workflow runs **every** pass with no selection flag; these flags exist for ad-hoc local runs and route by the `easy_apply` field rather than name so user-renamed passes still work.

1. **Fork this repo** on GitHub. Then **Settings → General → Change repository visibility → Make private**. Workflows hard-stop if the repo is public.

2. **Add GitHub Secrets** (Settings → Secrets and variables → Actions → New repository secret). Each `*_B64` secret is one file, base64-encoded. **Easiest: use the ⚙ Setup wizard — it encodes and writes all of these correctly.** To do it by hand, encode with the command for your OS:


   The workflows decode tolerantly (they strip certutil PEM wrappers and CRLFs) and, if a secret still isn't valid base64, fail with a message naming the offending secret instead of a generic abort.

## Running it for free

The whole loop is meant to cost nothing by default and to let money buy better
results rather than a working pipeline. Four things have to line up, and the
honest version of each is worth stating, because "free tier" hides a ceiling in
every one of them.

**Evaluation** runs on Gemini's API free tier. Capacity there is not the RPD
alone — the recommended row grants 14,400 requests/day against 16,000 TPM, and
an evaluation prompt is a whole JD plus the candidate profile at ~9,500 tokens,
so the token budget is what a run actually achieves: about **2,400 evaluations
a day**, which is ten times what a daily scrape produces, and about **two
requests a minute**, which is what the pipeline spends the day doing.

**The cloud** runs on GitHub Actions' Free plan: **2,000 Linux minutes a month
per ACCOUNT** for private repositories — not per repository. That is the number
the rest of this section is measured against, and the two rules it produces are
uncomfortable. First, conformance costs minutes: pacing 160–190 evaluations to
the recommended row's 16,000 TPM takes ~95–115 minutes of runner time, so a
daily at that length is ~3,000 minutes a month and does **not** fit. Second,
**one copy per GitHub account** — two copies of this template under one account
share the same 2,000 minutes and are over the budget at today's run length,
whatever each one costs alone. The way to reclaim minutes is the Setup wizard's
RPM/TPM/RPD boxes: the built-in table is a hand-copied free-tier snapshot and is
the fallback, while a project's real numbers from AI Studio (written to
`GEMINI_LIMITS_JSON` for the cloud and `config/gemini-limits.json` locally) are
authoritative for that key and are usually more generous — a looser token budget
is a shorter run, at the same quota. Failing that, the levers are the ones that
shrink the run: fewer search passes, a smaller `results_wanted`, a stricter
`min_score`. The digest's health line quotes each run's minutes and its ×30
projection so the arithmetic is visible before the month ends rather than after,
and warns inside the last 10%.

**Delivery** is a Discord webhook (two minutes to create, no account beyond the
server you already have) or SMTP, both free.

**Applying** runs on a free agent CLI. `DEFAULT_CLI` is `opencode`, which is
free with no key at all through its gateway's rotating hosted models, free with
an AI Studio Gemini key, and takes a paid Anthropic or OpenAI key without
changing anything else — one binary for both halves of the goal. The other free
entries carry smaller ceilings and say so in their own `tier_note` (a weekly
quota on `agy`, ~500 requests/day on a free `gemini` key ≈ 6–12 prepared
applications), because "free" without a number is how a person discovers the
ceiling half-way through an application.

**What paying buys**, in the order it is worth buying: a paid evaluation key
removes the pacing, which removes most of the minutes problem; GitHub Team or a
paid Actions minute top-up removes the budget; a paid agent CLI (`claude`, or a
paid key in `opencode`) is better at driving a browser through a long
application form than anything free. None of the three is required for the loop
to run end to end.

## Setup (one-time)

```powershell
./setup.ps1    # creates .venv, installs deps (core + UI), clones career-ops; points to the /onboard wizard for profile setup
```

Requires Python 3.12 (not 3.13 — jobspy pins numpy 1.26.3, no 3.13 wheel).

**NixOS** has a dev shell — `nix develop`, then `./setup.sh` as usual. It carries python312, node, `gh`, LibreOffice (for `--handoff-tailor`'s one-page fit), and two of the three free agent CLIs: `opencode` (`DEFAULT_CLI`) and `gemini-cli`, whose `mainProgram` is `gemini`, the `binary` [pipeline/agent_cli.py](pipeline/agent_cli.py) names. Both lag the versions the registry's flags were read off, same major; `npm install -g` works inside the shell for a newer one, because the shellHook points `NPM_CONFIG_PREFIX` at the user's home (npm's default global prefix is inside the read-only store). **`agy` is not there, and `pkgs.antigravity` is not it** — that attribute is `buildVscode`, the Antigravity *IDE*, while `agy` is a prebuilt dynamically-linked binary from antigravity.google that needs `programs.nix-ld` or an `autoPatchelfHook` derivation to start. The flake's `LD_LIBRARY_PATH` block does **not** cover that case: nix-ld is for foreign executables, and that block exists for Python wheels dlopening bare sonames — a distinction its own comment makes, and one that reads the other way at a glance. Playwright is the other thing the flake settles: `PLAYWRIGHT_BROWSERS_PATH` hands career-ops the nixpkgs browsers, because the chromium `npx playwright install` downloads is a generic-linux build that will not start here — so run the agent CLIs *from inside* `nix develop`, or Playwright MCP fetches its own and fails.
